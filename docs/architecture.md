# How it works

The React client owns navigation, lesson quizzes, and browser-local progress. `curriculum.ts` assembles typed course modules in `curriculum/`: mathematics, quantum mechanics, qubits/gates, software/compilation, algorithms, noise/QEC, error mitigation, hardware, applied optimization, tensor-network simulation boundaries, cryptography, chemistry, and machine learning. Twenty-seven courses contain 119 lessons across mathematics, quantum fundamentals, and applications. `LearningTrail.tsx` handles topic search, track filters, course expansion, and prerequisite navigation. `LessonDialog.tsx` presents explanations, mathematics or program syntax, worked examples, revealable practice, quizzes, and related lessons with focus trapping and background interaction disabled. Lessons can label their formula/program panel while existing math panels keep their default title. Prerequisites guide the order without locking access. See [the curriculum guide](curriculum.md).

Lesson lab links are discriminated unions: either a supported single-qubit gate sequence or one of the five existing named algorithm experiments. Opening an algorithm lesson selects its matching experiment, instead of substituting a single-qubit gate for a multi-qubit algorithm. The advanced molecular, noise/mitigation, cryptography, optimization-modeling, photonic, and ML lessons use guided calculations and workflow exercises; they do not add simulation endpoints.

The course order places mitigation after noise/QEC and applied optimization before Algorithm III's QAOA lesson. Cryptography I–II form one application branch, with Algorithm I's entanglement/oracle lessons recommended before QKD and Algorithm II's Shor/Grover lessons before post-quantum cryptography. Algorithm I retains the historical `grover-search` ID as an introduction; Algorithm II adds separate deeper search, amplification, walk, and QAE IDs. QAE follows both amplitude amplification and QPE. Existing v2 completion IDs remain valid when courses or lessons are inserted.

Software and Compilation follows Gates II. Hardware I–IV follows the circuit/software and noise foundations, progressing from microwave models through control descriptions, characterization, and Hamiltonian engineering. OpenPulse first appears as a software introduction and is developed in Hardware II. Classical–Quantum Boundaries I–III follows Algorithm III's variational background and progresses from tensor diagrams/Schmidt tools to one-dimensional solvers and other geometries. These courses use guided calculations and program/model interpretation; they add no execution endpoints or dependencies. Qiskit 2.0 Pulse removal and the archived/deprecated status of Qiskit Dynamics are explicit in the lessons and curriculum references.

`quantum.ts` evaluates 2x2 complex gate matrices for immediate feedback. It is intentionally restricted to one qubit. Probabilities follow Born's rule and Bloch coordinates retain relative phase.

The FastAPI service constructs allowlisted Qiskit circuits. `/api/simulate` returns initial and per-gate state snapshots, final exact amplitudes and probabilities, qubit-0 Bloch coordinates, circuit text, and finite-shot `StatevectorSampler` counts. `/api/algorithm` constructs the named two-qubit teaching circuits. Validation rejects invalid indices, unsupported gates, excessive shots, and oversized circuits. No user-supplied code is executed.

For a pure state α|0⟩ + β|1⟩, the Bloch coordinates are x=2 Re(α*β), y=2 Im(α*β), z=|α|²−|β|². For multiple qubits the API traces out the other qubits before computing qubit 0's vector. This is essential: a Bell pair's individual qubits are mixed, at the center, not pure arrows on the surface.

The QFT input is |01⟩, making the complex phase pattern observable in the returned amplitudes. The Grover oracle marks |11⟩ with CZ; one diffusion iteration suffices for this four-item case. QAOA uses RZZ(γ), then RX(−π/4) on both qubits for a one-edge MaxCut example. At γ=π/2, the cut probability reaches 1. The energy lab uses −ZI−IZ+0.5XX and an RY/CX ansatz; it is a toy model, not molecular chemistry or a complete optimizer. Angles are swept manually.

WebXR uses Three.js and the same browser statevector functions; it does not call itself a Qiskit execution. Unity calls the Python API through a bounded JSON request. Both map the Bloch z axis to world up. The native Unity starter requires an XR rig, interactables, platform settings, and hardware validation.

Progress schema: `qq.progress.v2`, an array of stable completed lesson IDs. `progress.ts` validates and deduplicates IDs. When v2 is absent, it reads `qq.progress.v1` indices using the fixed historical eight-lesson order, so inserting or reordering courses does not misassign completions. The next successful completion saves v2; reading progress does not write storage. XP is derived from unique completions at `XP_PER_LESSON = 25`, and reviewing a completed lesson cannot add XP. Blocked or corrupt storage falls back to session learning. A failed save shows a session-only notice and changes the learning spark's saving message. No backend account exists.

`achievements.ts` derives course badges, journey tiers, XP milestones, and the next badge from validated completion IDs. A course badge requires every current lesson in that course. All 27 courses have explicit badge titles, with “IF x == y? III” for Algorithm III. Tiers have fixed course thresholds (Bronze 1, Silver 9, Gold 18, Platinum 27), so adding courses does not raise those existing thresholds. Milestones use 2, 5, 10, 20, then every 20 lessons, plus the full curriculum; at 119 lessons the final checkpoint is 2,975 XP. At a completed checkpoint, the learning spark immediately targets the next one instead of staying capped at 50 XP.

`Achievements.tsx` renders the collection, tier requirements, milestone roadmap, learning spark, and dismissible reward announcements. Filters separate earned, in-progress, and unstarted badges. Badge actions open the first unfinished lesson, or the first lesson for review, while keeping the collection open behind the dialog. The learning trail previews the badge associated with each expanded course. Completion compares progress before and after to announce newly reached rewards once; revisiting lessons and reloading do not reannounce them. Badges and tiers are computed from saved lessons rather than stored as a second ledger, allowing existing progress to qualify automatically. These are cumulative milestones; date-based daily goals remain a separate roadmap item. See [achievement rules](achievements.md).
